# 研究：从曲库里的歌扒出「主旋律 + 和弦」

> 查询和实测日期：**2026-11-14**。只做研究和本机样品，没改 app 代码。
> 写法：每项先给结论。查不到原始依据的标「未核实」；根据资料推出来、还没实测的标「推断」。
> 公开仓库：这里不放任何歌曲素材、扒出来的谱、MIDI 或音频。样品只在本机（曲库旁边的 `扒谱样品/` 文件夹，不在仓库里）。

---

## 0. 一页结论

1. **主旋律：直接用波点现有的人声音高曲线，量化成音符就够用。** 在一首 130 BPM 的日语男声歌上实测：副歌 8 句里有 4 句的音符数和音节数完全对上，3 句差 1–2 个，1 句差 4 个；音高和 Basic Pitch 的结果基本一致。主要的错是**滑音被记成多余的短音**和**连唱的音没切开**，要留给用户手动改。
2. **定拍是关键，也是最容易出错的一步。** 样品第一版速度算成 129.17 BPM（实际 130），网格每 70 秒左右就错开半拍，旋律和和弦全乱。改成「逐拍累加」后拍点误差 8.8 ms。每一小节的第一拍在哪，只能靠和弦变化来推，**要让用户能手动挪**。
3. **和弦：自己写「色度 + 低音 + 模板 + HMM」，主歌够用，副歌一般。** 主歌出来的是很干净的 IV△7–V7–iii–vi（和低音对得上）；副歌有一段 3 小节都给成同一个和弦，还有猜错的。文献里这类方法的准确率在 70% 左右。授权干净、能在 Rust 里写。
4. **多乐器总谱：现在不做。** 真实流行歌上最好的模型「每个音 + 乐器都对」的 F1 也只有 20–40%，而且好的模型不是 GPL 代码就是非商用权重。
5. **自动重新编曲：现在不做进 app。** 能出 MIDI、授权干净、Mac 上能跑的只有 Anticipatory Music Transformer（全 Apache-2.0），可以本机试。其余的不是只出音频，就是权重授权没写。
6. **推荐方案见 §7**：Rust 里做「定拍 → 定调 → 旋律量化 → 和弦」，导出 MIDI + MusicXML，前端用 verovio 显示谱；全部只用 app 已有的数据，不加模型。

## 1. 主旋律

### 1.1 波点现有的音高曲线

- **怎么算**：`src-tauri/src/dsp/pitch.rs` 的 `detect`。YIN（差分函数用 FFT 加速），先降到 16 kHz，40 ms 窗，**10 ms 一帧**，范围 50–1000 Hz。输出每帧基频 `f0`（0 = 不发声）和可信度 `conf`。后处理：八度跳变折回、3 帧中值、去掉短于 40 ms 的发声段、短片段和前后 1.5 秒的旋律差太远就折回或丢掉（分离人声里漏进来的低音）。
- **谁来调**：`studio.rs` 的 `analyze_pitch` → `dsp/process.rs` 的 `analyze`。只接受曲库里的文件，输入就是「`<歌名> - 人声`」。
- **存在哪**：缓存目录 `pitch/<键>.json`（`{hop, f0[], conf[]}`）。键 = 文件路径 + 大小 + 修改时间 + `"pitch-v2"` 的哈希，所以人声文件不变就只算一次。资料清单 #30。

### 1.2 实测：把曲线量化成音符

样品流程（Python 原型，只在本机；正式做时搬到 Rust）：

1. 用 app 同一份 YIN 代码算整首人声的曲线。
2. **定调音偏差**：所有发声帧和最近半音的平均偏差（样品 +1 音分）。
3. **半音 HMM**：每帧一个半音状态，换音有代价，压住颤音和滑音的来回跳。
4. **滑音合并**：很短（< 150 ms）的音紧接一个差 1–2 个半音的音，并进后一个音；调外的短音贴着调内音，也并掉。样品里 922 个音并成 847 个。
5. **切同音**：同一个音高持续很久时，按人声的起音（onset）切开，一个字一个音。
6. **量化到 16 分音符网格**（网格来自伴奏定拍，见 §2）。

| 自查项（没有标准答案，只能这样查） | 结果 |
|---|---|
| 量化前的音符和 YIN 曲线同音（±50 音分）的帧 | 85% |
| 量化后 | 79%，覆盖 97% 的发声帧 |
| 副歌 8 句：音符数 vs 音节数（假名数，促音不算） | 4 句相等；3 句差 1–2；1 句差 4 |
| 副歌约 30 个音和 Basic Pitch 逐个对照 | 音高一致，只差在滑音那几个短音 |

**结论：够当起点，不够当成品。** 常见错误：
- 滑音、倚音被记成单独的短音，谱上冒出调外的还原号（比如 G♮ 紧接 G♯）。
- 连音（一个字唱好几个音）切得不准，有时多一个音、有时少一个。
- 量化到 16 分后，前倚和拖拍会被「拉直」，节奏读起来比实际规整。
- 男声按实际音高记在「高音谱号下加 8」上。

## 2. 定拍、定调、小节线

- **定拍**：伴奏轨做拍点检测（样品用 librosa 的 onset 自相关 + 动态规划，ISC 授权；正式做时在 Rust 里照这个思路写）。流行歌基本是恒定速度，所以用一条直线拟合所有拍点。**拍号要逐拍累加**（每两拍间隔除以中位间隔取整再累加），不能用「(时间 − 第一拍) ÷ 间隔」一把算，否则速度差 0.6% 就会在一分钟后错开半拍（样品第一版就是这样错的）。
- **定调**：伴奏的色度 + 人声的音高分布一起，和大小调模板比相关。只用伴奏时样品被判成 C♯ 小调（差一个五度），加上人声后是 A 大调，和弦走向也对得上。
- **第一拍**：先允许每一拍都换和弦，看换和弦最常落在哪一拍（样品：落在某一拍位 111 次，其他三个 42–74 次），那一拍就是小节第一拍。**这一步最不可靠**：前奏只有零星几下伴奏、或者有 2/4 小节时会错。要给用户「把小节线挪一拍」的按钮。

## 3. 和弦

| 方案 | 授权 | 能不能进 app | 准确率 |
|---|---|---|---|
| **自己写：CQT 色度 + 低音 + 模板 + HMM** | 自己的 | ✅ | 文献里同类方法在 Isophonics 上大小三和弦 69–74%（arxiv.org/abs/1612.05065） |
| BTC（双向 Transformer） | 代码 MIT；**权重授权未核实** | 先别 | 大小三和弦 WCSR 82.7（github.com/jayg996/BTC-ISMIR19） |
| Chordino / NNLS-Chroma、chord-extractor | GPL-2.0 | ❌ | 只能自己本机试 |
| madmom | 代码 BSD，**模型 CC BY-NC-SA** | ❌ | |
| autochord | Apache-2.0，但依赖 NNLS-Chroma（GPL） | ❌ | 作者自报 67% |
| essentia | AGPL | ❌ | |
| Omnizart | MIT | — | 官方说不支持 ARM Mac |
| Rust crate `kord` | MIT | 可以看 | 准确率没公布 |
| Rust crate `chord_detector` | GPL-3.0 | ❌ | |

**样品做法**：伴奏先去打击乐（HPSS），每拍取色度和低音（E1–E3）；模板用 大三 / 小三 / 属七 / 大七 / 小七；低音是根音加分，七和弦和调外和弦减分；HMM 只允许在半小节上换和弦。

**样品结果**：
- 主歌：每小节 Dmaj7 → E7 → C♯m → F♯m7（IV△7–V7–iii–vi），和低音一致，看起来是对的（没有人工核对，推断）。
- 副歌：有一段连续 3 小节都给成 Dmaj7，还零星冒出 Bm；低音明明在动。副歌伴奏更满、更失真，色度很乱。
- 前奏：伴奏只有零星几下，和弦在「有 / 无」之间来回跳。
- 自查：和弦根音 = 每拍最强低音的拍子占 56%；强拍上的旋律音是和弦音的占 58%。
- 七和弦的种类（△7 还是 7）基本是猜的。

**结论**：先自己写，期望 70% 左右，**主要价值是给出调内的大致走向，用户再改**。要更准再考虑 BTC（先确认权重授权，或者用可商用数据重训后导出 ONNX）。

## 7. 推荐方案

**只做「主旋律 + 和弦」，全部用 Rust 写，不加模型。**

1. **定拍**（新）：伴奏起音包络 → 自相关估速度 → 动态规划找拍点 → 逐拍累加后直线拟合。存进资料表（BPM、第一拍时间、小节线偏移），用户可以改。
2. **定调**（新）：伴奏色度 + 人声音高分布。
3. **主旋律**：现有 YIN 曲线 → 半音 HMM → 滑音合并 → 起音切分 → 16 分量化。
4. **和弦**：CQT 色度 + 低音 + 模板 + HMM，带调内先验，只在半小节换。
5. **输出**：MIDI + MusicXML，存在歌旁边（`<歌名>.melody.mid` / `.musicxml`，先在 `资料清单.md` 登记）；前端用 verovio（LGPL，WASM 单独加载）显示谱，用现有的播放器对着原唱听。
6. **必须有手动改**：挪小节线、删 / 合并音符、改和弦。自动结果只是起点。
7. 以后：Basic Pitch（ONNX）当旋律的第二意见；确认 BTC 权重授权后再考虑换和弦模型；编曲先在本机用 Anticipatory Music Transformer 试。

## 8. 没验证到的

- 只试了一首歌（日语、男声、130 BPM、4/4）。女声、快歌、变速、有 2/4 小节的歌都没试。
- 没有人工扒的标准答案，上面的数字都是自查，不是准确率。和弦对不对、小节线对不对，要用户听或者对照现成的谱。
- 「音高和 YIN 曲线一致」这一项是拿 YIN 自己当参照，对 YIN 方案有利。
- 研究部分的数字多数来自论文和项目页，没有在本机复现；标「未核实」的授权要问作者。
- 正式做成 Rust 后的效果、速度没测；样品的原型是 Python（只在本机虚拟环境里）。
